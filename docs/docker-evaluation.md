# Docker / Compose 评估：为什么不提供（对外发布前整备记录）

> 结论先行：**本次整备不新增 Dockerfile / docker-compose.yml**，维持
> [`deploy.md`](deploy.md) 的「裸机 runbook + 配置实例」形态。理由如下，
> 出现文末任一触发条件时再评审。

**1. 与仓库既有决策冲突，不应顺手推翻。**
[`deploy.md`](deploy.md) 开头的决策记录写明「单台 VPS + Caddy + pm2，不引入
Docker、Redis、对象存储」。这是发布基线的架构决策；把它改掉需要作者本人拍板，
而不是文档整备顺手带一个镜像进来。

**2. 对目标读者，Docker 是额外门槛而非简化。**
本次文档的唯一画像是不熟 Docker 的国内中小服主：装 Docker 引擎、理解 image /
volume / 网络映射，比照着 runbook 复制粘贴 `pnpm` 命令更难。而且构建镜像时
better-sqlite3 原生模块需要在容器内编译（Alpine 还要 musl 工具链），首次构建
慢、失败点更多——恰好违背「照着文档能跑通」的目标。

**3. 单进程硬约束让容器化收益归零。**
限流、人机验证、进程内缓存都是内存态，**只能单实例运行**
（[`deploy.md`](deploy.md) §7、[`ecosystem.config.cjs`](../deploy/ecosystem.config.cjs)
注释）。容器编排的核心收益（横向扩展、多实例编排）在本项目用不上；单机单容器
只是把 pm2/systemd 换了个名字，却多出镜像维护、卷挂载（`apps/server/data/`、
`UPLOAD_DIR`）、版本升级时数据卷兼容等一整套新问题。

**4. 维护成本与 CI 现实。**
仓库 CI 已覆盖三库矩阵与完整测试；新增 Dockerfile 意味着多一份需要与 `.nvmrc`、
pnpm workspace 布局、迁移产物同步维护的文件，而作者此前没有任何容器化使用痕迹，
交给一个没有容器环境的维护者验证 Docker 构建产物是不现实的。

**再评审的触发条件**（满足任一即可重开）：

- 出现第二套部署环境（预发布 / 多机房）或明确的 NAS / 面板用户一键部署需求；
- 有维护者愿意长期认领镜像构建、推送与版本发布；
- 限流/验证码/缓存改造成可外置（如 Redis），单进程约束解除。
