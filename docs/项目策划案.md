## 一、项目概述

### 1.1 项目定位
MCSerAuth 是一套面向 Minecraft Java 版第三方服务器团队的**一体化社区与身份认证系统**，由两大核心模块构成：

| 模块 | 定位 | 服务对象 |
|------|------|----------|
| 社区论坛 | 玩家讨论、攻略分享、公告发布的在线社区平台 | 全体注册玩家与游客 |
| 外置登录认证服务（Auth Service） | 基于开放认证协议的身份验证中枢，统一管理账户、皮肤、披风 | 网站用户、第三方启动器、服务器端 |

### 1.2 核心价值
- **统一账户体系**：一个账号打通「论坛 + 启动器 + 服务器」三端，避免多头注册。
- **开源合规协议对接**：认证服务遵循社区公认的 **Commons-Designs** 开放认证协议（authlib-injector 体系），可被主流第三方启动器（PCL2、HMCL、XMCL、TestWord 等）原生识别，无需修改客户端。
- **服务器准入控制**：只有经认证服务授权且被服务器白名单接纳的玩家才能进入游戏，形成完整的安全闭环。
- **个性化形象体系**：皮肤/披风由认证服务统一托管，玩家进入游戏后自动同步，成为社区运营的增值抓手。

### 1.3 设计原则
1. **模块高内聚、低耦合**：论坛与认证在代码层按 NestJS 模块严格划分，对外接口保持协议独立（认证 API 域名可单独暴露给启动器）；部署上采用单体应用换取最简运维，必要时可拆分。
2. **协议优先**：对外接口严格遵循 Commons-Designs / Minecraft 官方认证协议语义，避免自造协议导致启动器不兼容。
3. **账号安全第一**：密码哈希、令牌生命周期、会话管理按 Web 安全基线设计。
4. **开发环境最简**：单人可维护；不引入需要独立安装/运维的外部服务（数据库服务、Redis、对象存储均不采用）。

## 二、核心功能模块设计

### 2.1 社区论坛模块

#### 2.1.1 功能清单
- **用户体系**
  - 注册 / 登录（邮箱验证码 + 密码，预留 Minecraft 游戏账号联动入口）
  - 个人主页：头像、签名、发帖历史、皮肤预览卡片（从认证服务拉取）
  - 角色与权限：游客 / 注册玩家 / 审核员 / 管理员 / 超级管理员 / 超级后台（密钥）
- **版块与帖子**
  - 多级版块（建议初始：服务器动态、攻略交流、建议反馈、水区）
  - 发帖 / 回帖（Markdown + 图片上传）、楼层点赞、帖子置顶/加精/锁定
  - RSS /  sitemap 便于搜索引擎收录
- **通知系统**：回帖提醒、@提醒、系统公告（站内信）
- **运营工具**：敏感词过滤、举报处理队列、内容审核（先发后审可配置）、数据统计看板
- **与服务器联动（增值项）**
  - 玩家在线状态卡片（查询服务器 Server List Ping 协议）
  - 「我的服务器白名单状态」页面，与认证服务的玩家授权数据打通

#### 2.1.2 关键设计点
- **身份归属（已定稿）**：论坛帖子/用户互动挂在**网站账号（user）**上；发帖者在论坛的游戏身份表现由 `user` 关联的 `player`（UUID）提供，用于"游戏已认证"徽章、皮肤预览卡片等展示，不影响内容归属。

### 2.2 外置登录认证服务模块

#### 2.2.1 协议与接口设计
认证服务实现 **Commons-Designs 服务端 API**，主要端点分组如下：

1. **账户与授权（OAuth 风格）**
   - `GET /api/oauth/availability` — 授权页可用性检查
   - `GET /api/oauth/entry` — 启动器跳转的授权确认页（用户登录网站后确认授权）
   - `POST /api/oauth/authenticate` — 启动器用授权码/token 换取访问令牌
   - `POST /api/oauth/refresh` — 刷新访问令牌
   - `GET /api/user/profiles/me` — 获取当前用户档案
2. **Minecraft 会话服务（供服务器验证）**
   - `POST /api/session/joinServer` — 客户端加入服务器时向服务器推送会话（需玩家服务端 ID 在白名单内）
   - `POST /api/session/hasJoined` — 服务器查询某 IP 的最近会话，用于登录校验
3. **玩家档案服务（供服务器 mod 调用）**
   - `GET/POST /api/profiles/`（by uuid/name）、`/api/profiles/minecraft`（批量）、`/minecraft/profile/skins`、`/minecraft/profile/capes` — 皮肤/披风的上传、设置、查询与纹理 URL 下发

#### 2.2.2 皮肤与披风子系统
- **托管方式**：纹理 PNG 存储于本地磁盘目录（`/data/uploads`），通过应用层签名 URL 控制访问有效期
- **玩家功能**：上传皮肤（严格校验 64×32 / 64×64 / 半透明）、上传披风（64×32 固定规格，仅授权用户可见）、皮肤库（官方预设皮肤 + 收藏）、切换当前皮肤/披风
- **审核链路**：上传纹理进入待审状态（人工 + 尺寸/内容校验），通过后下发至服务器缓存
- **分发协议**：完全复用 Commons-Designs `Profile/Textures` 数据结构，服务端 mod（如 SkinRestorer）可直接消费

#### 2.2.3 账号与准入关键规则（✅ 已定稿）
- **三层身份分离**：网站账号（user，better-auth 管理）/ 游戏身份（player，UUID 终身不变）/ 形象资产（皮肤披风，挂 UUID）各自独立建模，用 UUID 串联；改名、换肤、重置密码互不牵连。
- **改名策略**：开放改名，同一 player 30 天冷却一次；旧昵称保留 30 天（仅本人可改回）；曾用名历史入后台可查。
- **双令牌体系**：网站会话（Cookie，better-auth）与启动器令牌（Access/Refresh，Commons-Designs OAuth）共存于同一账号；退出网站登录不影响启动器；玩家可在"已授权设备"页自主吊销任意启动器令牌（进 M3 MVP）。
- **授权页实现**：授权确认页及"请先登录"页由 **NestJS 模板直出**（与登录态同源，避免跨工程 Cookie 问题，全项目唯一渲染例外）。
- **封禁规则**：认证侧 `banned` 标记在 hasJoined 拦截，**下次登录起全域生效**（不开发 Paper 插件，游戏内即时处置由服主使用服务器自带命令）；封游戏默认连封论坛，后台可单独控制。

#### 2.2.4 准入与安全子系统
- **服务端白名单**：管理员登记允许接入的服务器ID/密钥，只有白名单内服务器能执行 `hasJoined` 校验
- **令牌体系**：短期访问令牌（默认 30 天可配）+ 刷新令牌轮换 + 设备授权记录（玩家可查看并吊销）
- **风控**：登录失败限频、IP 异常告警、关键操作邮箱二次确认

## 三、技术架构（✅ 已定稿）

### 3.1 总体架构
```
 第三方启动器             浏览器                Minecraft 服务器
 (PCL2/HMCL，Java)         │              (Paper + authlib-injector,
      │                    │               服主自行部署，与我们无关)
      └─────────┬──────────┴──────────┬───────────┘
                │ HTTPS               │ HTTPS
         ┌──────▼──────┐              │
         │ Caddy 反代   │──────────┐  │
         │ (域名路由/TLS)│          │  │
         └──┬───────┬──┘          │  │
            │       └─────────────┘  │
   ┌────────▼───┐      ┌─────────────▼──────────┐
   │ Next.js    │ API  │ NestJS 单体后端          │
   │ 前端工程    │─────▶│ ┌────────┐ ┌─────────┐ │
   │ (pm2 进程)  │      │ │论坛模块 │ │认证模块  │ │
   └────────────┘      │ │(better-│ │(Commons-│ │
                       │ │ auth)  │ │ Designs)│ │
                       │ └───┬────┘ └───┬─────┘ │
                       └─────┼──────────┼───────┘
                       SQLite 单文件库 + /data/uploads(皮肤/附件)
                       (会话/限频用进程内存，不引入 Redis)
```

### 3.2 技术选型（✅ 已定稿）

> 决策原则：开发环境最简、单人可维护、Node.js 成熟生态、现代化。

| 层 | 定稿选择 | 说明 |
|----|---------|------|
| 工程形态 | **pnpm monorepo**：`apps/web`（Next.js）+ `apps/server`（NestJS），共享 TS 类型包 | 一个仓库两个工程 |
| 后端分工 | **NestJS 全包**：注册登录、论坛业务、认证协议、皮肤披风全部在 NestJS；Next.js 只做页面渲染 | API 层独立，将来做 App/小程序可直接复用 |
| 语言/运行时 | TypeScript + Node.js 22 LTS | 全栈统一 TS |
| 后端框架 | NestJS | 路由/校验/DI/定时任务内置，免自己搭架构 |
| 网站登录 | better-auth（接在 NestJS 侧） | 邮箱密码、会话、验证码开箱即用 |
| 认证协议 API | 手写实现 Commons-Designs 端点（Controller + DTO 对照协议文档） | Node 生态无现成库；协议为纯 HTTP+JSON，语言无关，预计约 1 周工作量 |
| 前端 | **Next.js**（App Router） | 定稿；SSR 利于论坛 SEO 收录 |
| 数据库 | **SQLite（WAL 模式）+ Drizzle ORM** | 零安装零配置，备份=复制文件；性能支撑数千日活无压力；瓶颈时可低成本迁移 PostgreSQL |
| 缓存/会话 | 进程内存 + SQLite（**不引入 Redis**） | 减少一个运维组件 |
| 文件存储 | 本地磁盘 `/data/uploads`（**不引入对象存储**） | 皮肤纹理与论坛附件 |
| 图片处理 | sharp | 皮肤 PNG 尺寸/格式校验与规范化 |
| 密码哈希 | argon2（argon2 npm 包） | 安全基线要求 |
| 邮件 | Nodemailer（或 Resend API） | 注册验证码、通知 |
| 部署 | **Caddy（HTTPS 反代）+ pm2（两个 Node 进程）** | 服务器需开放的内容只有 Node.js，不需要 Java/Docker |

**取舍说明**：
- 放弃 MySQL/Redis/MinIO 等"多一个服务"的组件，换取 `git clone → npm install → npm run dev` 即跑通的体验。
- SQLite 的真实边界（多机共写/几十 GB 数据量）本项目均不触及；届时 Drizzle 迁移 PG 改动面可控。

### 3.3 服务器端对接方式（Java 侧归属说明）
- **重要认知**：Commons-Designs 是语言无关的 HTTP+JSON 协议。Java 只存在于**别人的两端**（启动器、MC 服务器），我们的服务端纯 Node，无需任何 Java 环境。
- authlib-injector 是一个几百 KB 的 jar，由**服主**加在他原有的 Paper 启动参数中（`-javaagent:authlib-injector.jar=https://auth.域名`），`server.properties` 设 `online-mode=false`——服主本来就用 Java 跑 MC，**零新增环境负担，且不由我们维护**。
- 皮肤同步：认证服务下发纹理 URL，服务端配合 **SkinRestorer** 等插件消费档案 API。
- 项目内**不开发 Paper 插件、不修改启动器**，仅交付符合协议的 HTTPS 服务。

### 3.4 安全基线
- 全站强制 HTTPS（Caddy 自动签发续期 Let's Encrypt 证书）；Cookie 属性 `Secure/HttpOnly/SameSite=Lax`
- 密码使用 **argon2id**（argon2 npm 包，非纯 JS 实现）
- 授权页抵御 CSRF（state 参数）；启动器回调校验 redirect 白名单
- 皮肤上传由 sharp 严格校验文件类型/尺寸（64×32 / 64×64），恶意内容扫描预留接口
- 敏感日志脱敏，令牌只存哈希

## 四、用户流程分析

### 4.1 玩家首次注册并进入游戏（核心链路）
```
1. 访问网站 → 注册（邮箱验证）→ 完善资料（可传皮肤）
2. 打开第三方启动器 → 账户管理 → 添加外置登录 → 输入认证服务地址
3. 启动器请求 /api/oauth/availability → 跳转浏览器授权页（已登录则直接确认）
4. 玩家点击「授权」→ 启动器获得令牌 → 本地显示玩家昵称与 UUID
5. 玩家选择服务器进服 → 客户端 joinServer → 服务器 hasJoined 校验 → 通过，进入游戏（皮肤自动加载）
```
**关键体验点**：步骤 2 只需配置一次；步骤 3 若浏览器未登录网站，需引导先登录再回到授权页，避免流程断裂。

### 4.2 论坛互动流程
浏览（游客）→ 注册/登录 → 发帖/回帖 → 收到通知 → 回访，形成留存闭环；违规内容经举报/审核进入版主处理队列。

### 4.3 管理员流程
后台登录 → 用户管理（封禁/解封）→ 服务端白名单登记 → 皮肤审核队列 → 公告发布 → 数据看板（DAU、注册转化、进服人数）。

### 4.4 异常流程（必须覆盖）
- 令牌过期 → 启动器自动 refresh；refresh 失效 → 重新走授权页
- 玩家改名：UUID 终身不变，30 天冷却，旧名保留 30 天仅本人可改回（→ 2.2.3）
- 令牌被盗/设备遗留 → 玩家自助"已授权设备"页吊销（M3 提供）
- 封禁 → 认证侧标记，下次登录起所有对接服务器生效；论坛同步默认连封（→ 2.2.3）
- 服务器未在白名单 → joinServer 返回明确错误码，指引服主联系管理方

## 五、开发计划

### 5.1 里程碑（按 4 人团队、单人周投入估算，可按实际调整）

| 阶段 | 周期 | 交付物 | 退出标准 |
|------|------|--------|----------|
| **M0 奠基** | 2 周 | pnpm monorepo 脚手架（web+server）、SQLite Schema 设计稿、API 契约文档（OpenAPI） | 认证服务全部接口契约评审通过；本地 `npm run dev` 双工程启动 |
| **M1 认证核心** | 4 周 | 账户体系（better-auth）、OAuth 授权链路、session joinServer/hasJoined | HMCL/PCL2 完成登录，Paper 测试服（服主侧装 injector）可进服 |
| **M2 皮肤披风** | 3 周 | 纹理上传（sharp 校验）/审核/分发、Profile API | SkinRestorer 环境内游戏内皮肤生效 |
| **M3 论坛 MVP** | 4 周 | Next.js 页面 + NestJS 论坛接口：注册登录、版块、发帖回帖、基础后台 | 论坛核心功能可用，与认证共享同一账号体系 |
| **M4 运营与加固** | 3 周 | 审核队列、通知、限频风控、管理看板、文档站 | 安全自查清单通过，压测登录链路达标（SQLite 单机目标下调为 ≥200 QPS） |
| **M5 Beta 上线** | 2 周 | Caddy+pm2 生产部署、公告、灰度邀请 50 名玩家 | 一周内无 P0 故障 |

合计约 **18 周（4.5 个月）** 达成 Beta。

### 5.2 团队分工建议（按全栈 TS 团队设定，单人开发则按顺序串行执行同样里程碑）
- NestJS 后端：M1 认证协议 → M2 纹理 → 论坛 API
- Next.js 前端：M0 介入脚手架与 UI 体系 → M3 论坛页面 → 管理后台
- 运维（可兼）：Caddy/pm2 部署、CI、Paper 测试服对接（测试服的 injector 配置由我们自己临时搭一个验证环境）、文档
- 社区运营（可兼）：版块规划、皮肤库素材、内测招募

### 5.3 后续迭代方向（Beta 后）
- 玩家侧「授权设备管理」页面
- 服务器状态页 / 白名单自助申请流程
- 皮肤商城、披风分级（贡献点解锁）等社区激励
- 开放 API：允许服主查询自家玩家数据（只读、限权）

## 六、风险与对策

| 风险 | 影响 | 对策 |
|------|------|------|
| Commons-Designs 协议细节实现偏差导致启动器不兼容（Node 无参考实现可抄） | M1 验收失败 | M0 阶段用 HMCL/PCL2/authlib-injector 做契约级联调；保留官方协议文档逐条对照 checklist |
| 认证服务成为单点，宕机则全服无法进人 | P0 事故 | 单体部署下：pm2 自动重启 + SQLite 文件定时备份 + session 结果短缓存；状态页 + 告警；规模上来后再拆独立认证进程 |
| 皮肤上传滥用（违规图、超大文件） | 运营/法律风险 | sharp 严格尺寸校验 + 审核队列 + 单用户配额 |
| 撞库/暴力破解 | 账号安全事故 | argon2id + 限频 + 验证码 + 异常登录通知 |
| 范围膨胀（论坛功能无止境） | 延期 | M3 只保 MVP 清单，其余进 backlog |

## 七、决策记录与待决事项

### 7.1 已定稿 ✅
| # | 事项 | 结论 | 备注 |
|---|------|------|------|
| D1 | 后端技术栈 | **NestJS（TypeScript + Node 22）** | 决策原则：开发环境最简、单人可维护、Node 成熟生态 |
| D2 | 前端 | **Next.js** | SSR 利于论坛 SEO；与后端同仓库 monorepo |

| D4 | 数据库 | **SQLite（WAL）+ Drizzle**，不引入 MySQL/PG | 瓶颈时低成本迁移 PG |
| D5 | 组件瘦身 | 不引入 Redis/对象存储/Docker，部署 Caddy+pm2 | 服务器只需 Node 环境 |
| D6 | Java 边界 | 不写 Paper 插件、不维护 injector，仅交付协议 API | Java 在启动器/服主侧，协议语言无关 |
| A1 | 身份模型 | 三层分离：user / player(UUID 终身不变) / 形象资产 | 帖子归 user，游戏身份仅作展示/徽章 |
| A2 | 改名 | 开放：30 天冷却 + 旧名保留 30 天 + 曾用名入后台 | UUID 不变，服务器资产不受影响 |
| A3 | 授权页渲染 | NestJS 模板直出（全站唯一例外） | 与登录态同源，照皮肤站标准做法 |
| A4 | 设备管理页 | "已授权列表+吊销"进 M3 MVP | 令牌唯一自助回收通道 |
| A5 | 封禁 | 认证侧标记，下次登录生效；论坛/游戏默认连封 | 不写插件，游戏内即时处置归服主 |
| S1 | user:player 关系 | 严格 1:1（UNQ 约束） | 将来开放多角色再改 1:N，表结构不变 |
| S2 | 皮肤/披风 | 共用 `skin` 表（kind 字段区分） | 二者结构一致，仅尺寸校验不同 |
| S3 | 权限模型 | `user.role` 枚举（user/reviewer/admin/superadmin），不建 RBAC 表 | 单体小项目不需独立权限框架 |
| S4 | 曾用名存储 | `player.nickname_history` JSON 字段，不独立建表 | 改名频率低，省表 |
| S5 | 删除策略 | 软删除（打标记不真删） | 安全可追溯；令牌/举报/帖子均适用 |
| S6 | 冗余计数 | **不预存** `post.reply_count`，实时 COUNT | 初期量小，符合“能省则省”，性能不够时再加 |

### 7.2 待决 ⏳

### 附.3 论坛岛

**`category`**：id(PK) / name / slug(UNQ) / description / sort_order / parent_id(自引用)
