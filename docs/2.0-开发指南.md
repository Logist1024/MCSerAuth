# MCSerAuth 2.0 开发指南

> 版本：v1.0（2026-10-31）｜基线：`main` @ `8babe91`（1.x 功能收官状态，`package.json` 版本 `0.1.0`）
> 读者：本项目的维护者与后续协作者。本文回答三个问题：2.0 从哪里出发、要做哪些事、做到什么程度算完成。
> 与 [`项目策划案.md`](项目策划案.md) 的关系：策划案定义了 1.x 产品范围（M0–M5）。本文在策划案之上规划
> 2.0：**兑现其中未完成的 M5**，并追加「质量还债」与「生态扩展」两个批次。与策划案冲突之处
> （如 D4/D5 已被 [ADR 0006](adr/0006-multi-database.md) 推翻），以 ADR 与本文最新决策为准。

## 1. 版本定位

1.x 已把「策划案 + M4.5 扩展」的功能面基本做完：认证（OAuth 授权码 + PKCE、authlib-injector
兼容层）、会话服务、皮肤披风、论坛（版块/帖子/回复/点赞/通知/举报）、成长体系（等级/称号/签到/
积分/商店/打赏/Banner）、四级角色 + 能力下放后台 + 密钥超级控制台、人机验证、RSS/sitemap、
三库支持。OpenAPI 已登记 **102 路径 / 121 操作**（基线时点；F5 新增两个探针后为 104 / 123），
单一逻辑模型 **29 张表**。

但它还不是一个「可以放心上线的正式版」：

- 协议字段全部未经官方文档核对（10 项待核），启动器真机联调从未执行（M0 遗留 P0）；
- MySQL / PostgreSQL 只在测试断言层面自洽，真实迁移、`db:copy-data` 端到端、CI 数据库矩阵
  首跑均未验证；
- 测试只覆盖 service 层，没有 HTTP 层 e2e（supertest 已装未用）；前端约 1.4 万行代码只有
  1 个测试文件；
- 若干超大规模文件（1240 行的成长服务、931 行的前端 API 客户端）与 admin 面板重复样板正在
  抵消模块化的收益。

因此 **2.0 的主题是「从功能齐备到生产可运营」**，分三个里程碑推进：

| 里程碑 | 主题                 | 一句话目标                                                                  |
| ------ | -------------------- | --------------------------------------------------------------------------- |
| **M5** | 生产就绪与协议可信化 | 兑现策划案 M5：真机联调、真实多库验证、安全加固、部署与备份上线             |
| **M6** | 架构还债与质量       | 补齐两端最薄弱的测试层，拆分最大的服务，收敛已知 hack                       |
| **M7** | 生态与运营扩展       | 落地策划案 §5.3 遗留方向：服务器状态/白名单自助、开放只读 API、设备管理回归 |

依赖关系：M5 与 M6 互不依赖，可并行推进；**M7 必须在 M5 协议可信化收敛之后开始**——它新增的
对外能力（服务器状态、开放 API、设备管理）都要建立在协议语义稳定的前提上。

## 3. 2.0 总体规划

### 3.1 目标与非目标

**目标**：

1. 一套真实环境验证过的发布物：至少一款主流启动器真机全链路可用，MySQL/PG 迁移与数据搬迁
   真实跑通，一条从空 VPS 到上线的文档化路径。
2. 质量底线：核心业务链路有 e2e 保护，前端关键交互有组件测试，CI 三矩阵全绿。
3. 两个运营闭环（M7）：服务器状态/白名单自助申请、设备令牌自助管理；一个可选开放面：只读 API。

**非目标（延续策划案红线，2.0 仍然不做）**：

- 不写 Paper 插件、不修改任何启动器（策划案红线，永不实施）；
- 不引入 Redis / 对象存储 / Docker（D5 维持：单机 Caddy + pm2 是 2.0 的部署形态；确有多实例
  需求时再作为 3.0 议题重新评审限流与会话的外置化）；
- 不做游戏内即时封禁处置（归服主）；不建 RBAC 表（S3 维持：四级枚举 + `user_permission` 下放够用）；
- 不支持高清皮肤（仅原版尺寸，ADR 0005 维持）。

### 3.3 版本与分支策略

- **发布基线**：启动 2.0 开发前，给当前 `main` 打 `v1.0.0` tag 并将 `package.json` 版本统一
  升至 `1.0.0`（现状功能已完成、M4.5 收官，值得一个可引用的基线；避免「0.1.0 直接跳 2.0」的
  断层）。**已完成**（2026-10-31：tag `v1.0.0` 已打，四处 `package.json` 均为 `1.0.0`，
  `APP_VERSION` 改为由 `package.json` 派生）。
- **分支**：沿用 trunk-based——工作项直接在 `main` 上按 Conventional Commits 小步提交，
  每个工作项一个原子提交集；不做长周期 feature 分支（单人维护，长分支只会放大合并成本）。
- **2.0 过程版本**：M5 完成时发布 `2.0.0-alpha.1`；M6 完成时发布 `2.0.0-beta.1`；GA 打
  `v2.0.0`。apps/web、apps/server、packages/shared 三处版本号始终一致（发布提交里一次改齐）。
- **ADR**：F2 的基线对齐、F8 的 e2e 形态、F13 的鉴权模型各写一篇 ADR（编号自 0007 起）。

## 4. M5 — 生产就绪与协议可信化

### 4.1 F1 协议真机联调与字段核对（P0）

**目标**：把 T1 关掉——协议语义从「按惯例推定」变成「真机验证过」。

**范围**：

1. 真机联调至少两款启动器（推荐 HMCL + PCL2，覆盖两种实现风格）：
   - authlib-injector 直登（认证服务器地址填 `http://<host>/api`，邮箱 + 密码登录）；
   - 浏览器 OAuth 授权码 + PKCE 全链路（entry → authenticate → refresh → profiles/me）；
   - joinServer / hasJoined 进服验证与皮肤披风显示。
2. 对照抓包结果逐项核对 [`protocol-checklist.md`](protocol-checklist.md) §4 的 10 项待核：
   hasJoined 字段与 204/403 语义、profiles 命名空间职责、纹理字段常量、multipart 字段名、
   签名需求、令牌有效期定值、自动建 player 策略、`server_entry.secret` 用途等。
3. 有偏差的字段改 `packages/shared/src/protocol/*` 与对应服务，刷新 `pnpm openapi:export`，
   并在 checklist §5 记变更。

**验收**：两款启动器真机注册、登录、进服、皮肤显示全部通过；§4 清单 10 项全部标注
「已核（附启动器与版本号）」或「转 issue 挂起并说明原因」。

### 4.2 F2 多数据库真实验证与迁移基线对齐（P0）

**目标**：把 T2、T3 关掉——MySQL 8.0 / PostgreSQL 16 从「测试断言自洽」变成「真实跑通」。

**范围**：

1. 准备真实库环境（本机无 Docker，可用 GitHub Actions service container 或临时云主机；
   `.github/workflows/ci.yml` 的 `test-databases` job 已就绪，推动首跑并保持常绿）。
2. 真实验证清单：空库迁移 → `pnpm db:copy-data` 端到端搬迁（含 SHA-256 行校验）→ server 全部
   测试在两库上通过 → `db:migrate` 幂等重跑。
3. **迁移基线对齐（需 ADR 0007）**：当前 SQLite 有 12 版迁移历史而 MySQL/PG 只有 0000 基线。
   建议方案：以当前 29 表状态为三方共同基线重新生成 0000，存量开发 SQLite 库用
   `db:copy-data` 搬迁到新基线；此后三库迁移永远成对生成。备选方案（保持 SQLite 历史并文档化
   「新装走 0000、存量走 12 版」）仅在出现无法搬迁的存量部署时采用。
4. 按 [`database.md`](database.md) 已知问题做一次回归确认：utf8mb4 建库、`nullsLast()` 排序、
   `active_slot` 判别列、时间戳单位差异。

**验收**：CI 三 job 首跑并保持常绿；MySQL/PG 上迁移、搬迁、测试三项证据（命令输出）归档进
[`refactor-multi-db-report.md`](refactor-multi-db-report.md) 的「待验证项」章节并关闭；ADR 0007 合入。

**状态（2026-11-01）：已完成**。ADR 0007 合入，三方言各剩一份 29 表 `0000` 基线；
`test-databases` 矩阵补上 copy-data 端到端步骤后，首跑连续四次在真实 MySQL/PG 上失败，
暴露并修复了 3 个只有真库才能发现的缺陷（慢查询包装器吞掉驱动返回值、`--` 参数分隔符被吃掉、
table extras 声明的复合主键未被识别），第五次推送
[run 41162131163](https://github.com/Logist1024/MCSerAuth/actions/runs/41162131163)（`dc503db`）
四个 job 全绿；空库迁移、全量测试、SQLite→MySQL/PG 搬迁（含 SHA-256 全行校验与目标库幂等重跑）
