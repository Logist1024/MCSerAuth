> 依据：《docs/项目策划案.md》v1.2（技术栈与决策已定稿）
> 适用阶段：**M0 奠基**（约 2 周）——本文是开发期的过渡性约定，业务实现（M1+）启动后逐步替换为正式文档。

## 一、底座目标与范围

### 1.1 本阶段要交付的
| # | 交付物 | 说明 |
|---|--------|------|
| 1 | pnpm monorepo 脚手架 | `apps/web` + `apps/server` + `packages/shared`，Node 22 LTS |
| 2 | 公共基建 | env 校验、统一错误码与异常过滤、DTO 校验、日志（脱敏）、健康检查 |
| 3 | 数据层 | SQLite（WAL）+ Drizzle，全部 15 张表的首版迁移脚本 |
| 4 | better-auth 接线 | 在 NestJS 侧完成接入，session/account/verification 自动建表，注册/登录冒烟通过 |
| 5 | API 契约 | NestJS Swagger 产出 OpenAPI；Commons-Designs 全部端点以 stub 形式登记 + 协议对照 checklist |
| 6 | 契约级联调 | HMCL/PCL2 指向 stub 端点验证连通性与响应结构 |
| 7 | DX 与 CI | `pnpm dev` 一键双起、`.env.example`、README 开发手册、GitHub Actions（lint + typecheck + build） |

### 1.2 本阶段明确不做的
- OAuth 授权业务链路、session 令牌签发（M1）
- 皮肤/披风上传与分发（M2）
- 论坛页面与业务接口（M3）
- 生产部署、Caddy/pm2（M5）
- Paper 插件、启动器修改（永不，见策划案 D6）

## 二、工程结构约定

```
MCSerAuth/
├── apps/
│   ├── server/                # NestJS 单体后端（全业务）
│   │   ├── src/
│   │   │   ├── main.ts
│   │   │   ├── app.module.ts
│   │   │   ├── config/         # env 加载与 zod 校验
│   │   │   ├── common/         # 过滤器、管道、拦截器、公共 helper（软删除等）
│   │   │   ├── db/             # Drizzle 实例、schema、迁移
│   │   │   └── modules/        # 业务模块，按岛划分（见下）
│   │   └── drizzle/            # 迁移 SQL 输出
│   └── web/                    # Next.js App Router，只做渲染
├── packages/
│   └── shared/                 # 跨端 TS 类型 / DTO / 错误码 / zod schema（单一事实来源）
├── docs/
└── .github/workflows/ci.yml
```

**NestJS 模块划分（与策划案的三个"岛"对齐，保持 M0 只建骨架）：**

| 模块目录 | 岛 | M0 状态 |
|----------|----|---------|
| `modules/auth` | 账号认证（better-auth + Commons-Designs oauth） | better-auth 接线 + stub 端点 |
| `modules/session` | MC 会话服务（joinServer/hasJoined） | stub 端点 |
| `modules/profiles` | 玩家档案与形象资产 | stub 端点 |
| `modules/forum` | 论坛 | 目录占位 |
| `modules/admin` | 管理与审核 | 目录占位 |

## 三、环境与启动

### 3.1 环境
- Node.js **22 LTS**（`.nvmrc` 固定 `22`；`package.json` 写 `engines`）
- pnpm ≥ 9（`corepack enable`）
- 可选浏览器启动器（HMCL 或 PCL2）用于契约联调

### 3.2 一次性安装与启动
```bash
git clone <repo> && cd MCSerAuth
corepack enable
pnpm install
cp .env.example apps/server/.env   # 后续按需
pnpm db:migrate                    # 建 SQLite 库 + 全部迁移
pnpm dev                           # 同时启动 web(:3000) 与 server(:8000)
```

### 3.3 端口与域名约定（已拍板）
| 项 | 定值 |
|----|------|
| web 端口 | `3000` |
| server 端口 | `8000` |
| API 前缀 | `/api/*` |
| 本地调用方式 | web 直连 `http://localhost:8000`（不强制走反代；Caddy 只在 M5 部署时上岗） |
| 认证域 | env 中按「站点域 + 认证域分离」占位（`APP_URL` / `AUTH_URL`），本地均填 `http://localhost:*`，待域名定稿后只改配置不改代码 |
| Cookie | 本地 `Secure=false`，生产强制 `Secure/HttpOnly/SameSite=Lax`（策划案 3.4） |

### 3.4 仓库脚本（根 package.json）
```jsonc
{
  "scripts": {
    "dev": "并行启动 apps/server 与 apps/web 的 dev",
    "build": "先 shared，再 server、web",
    "lint": "全仓 ESLint",
    "typecheck": "tsc --noEmit（全仓）",
    "db:generate": "drizzle-kit generate",
    "db:migrate": "drizzle-kit migrate",
    "db:studio": "drizzle-kit studio"
  }
}
```

## 四、编码规范

### 4.1 TypeScript
- `strict: true`，禁止 `any` 裸用（`unknown` + 收窄）
- 跨端共享的 DTO / 枚举 / 错误码**只写在 `packages/shared`**，apps 内不得自行复制类型

### 4.2 命名
- 文件：类与模块 PascalCase 文件名（NestJS 惯例）；组件文件 PascalCase；工具函数 camelCase
- 数据库：snake_case 表名与列名；Drizzle 定义与附录 Schema 一一对应
- 环境变量：全大写 `SCREAMING_SNAKE_CASE`，集中在 `apps/server/src/config/` 校验导出

### 4.3 提交与分支
- Conventional Commits（`feat:` `fix:` `chore:` `docs:` …），M0 期间单人主干开发 + feature 分支合并
- git hooks：pre-commit 跑 lint-staged（ESLint + Prettier）

### 4.4 错误与日志
- 统一响应形状：成功 `{ code: 0, data }`；错误 `{ code: <业务错误码>, message }`
- **例外**：Commons-Designs 端点响应**必须逐字段对照协议文档**，不得套统一包装（协议优先，见策划案 1.3 原则 2）——stub 阶段就以协议原生形状返回
- 日志用 pino；令牌、密码、IP 出日志前一律脱敏；令牌只存哈希（附录 `token` 表）

## 五、数据层约定

- SQLite + **WAL 模式**（连接参数中显式开启），better-sqlite3 驱动
- Drizzle ORM；**所有建表改动必须走 drizzle-kit 迁移**，禁止手改线上库、禁止运行时同步
- 已定稿决策落库时必须体现（写实现时自查）：
  - **S1** `player.user_id` UNIQUE（user:player 严格 1:1）
  - **S2** `skin.kind` 区分皮肤/披风，共用一张表
  - **S4** 曾用名存 `player.nickname_history`（JSON），不建独立表
  - **S5** 软删除：`token.revoked_at`、举报/帖子状态标记，一律不物理删
  - **S6** 回帖数等计数**实时 COUNT**，不预存
  - **S3** 权限就是 `user.role` 枚举，不建 RBAC 表
- better-auth 的三张表（session/account/verification）由其自动维护，**不进手写迁移**，但 drizzle 类型声明中要引用，保证事务与查询类型安全

## 六、API 契约与协议对照（M0 关键任务）

1. NestJS 开启 Swagger，OpenAPI 随构建产出，作为**接口契约的唯一事实来源**
2. Commons-Designs 以下端点在 M0 以 **stub Controller** 登记（可返回 501 或最小合法结构）：
   - `GET /api/oauth/availability`、`GET /api/oauth/entry`、`POST /api/oauth/authenticate`、`POST /api/oauth/refresh`、`GET /api/user/profiles/me`
   - `POST /api/session/joinServer`、`POST /api/session/hasJoined`
   - `GET/POST /api/profiles/*`、`/api/profiles/minecraft`、`/minecraft/profile/skins`、`/minecraft/profile/capes`
3. 对每个端点建 **协议对照 checklist**（请求字段/响应字段/状态码/错误码 ↔ 协议文档），存 `docs/protocol-checklist.md`
4. 用 HMCL/PCL2 指向 `http://localhost:8000` 做连通性冒烟，把「启动器实际发出什么」记录进 checklist——这是对冲风险 #1（协议偏差导致启动器不兼容）的核心手段
